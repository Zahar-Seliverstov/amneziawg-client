# Правила маршрутизации: почему медленно и что делать

Отчёт по анализу механизма добавления и удаления правил, 2026-09-04.

## Что происходит сейчас

Одно правило — это полная пересборка всей маршрутизации.

`handleAddRoutingRule` (`backend/internal/api/server.go:399`) → `saveConfig()` +
`applyRoutingNow()` → `ApplyRouting` (`backend/internal/vpn/routes.go:88`) →
`configureTraffic` (`routes.go:31`), под `routeMu`, синхронно в обработчике HTTP:

1. `stopNameRouting()` — гасит DNS-посредника и **сбрасывает все выученные
   динамические маршруты** (`set.Clear()`), по одному `exec ip route del` на каждый.
2. `flushRoutes()` — снимает все свои маршруты, снова по `exec` на штуку.
3. `configureRouting()` — заново перебирает **все** правила: каждый домен
   резолвится последовательно, по 5 с таймаута (`nameroutes.go:249`); каждый
   адрес — `exec ip route add`; в режиме `direct_list` дополнительно `PathTo`
   (ещё `exec`) на каждый адрес и `net.LookupIP` на endpoint сервера.
4. `startNameRouting()` — новый посредник, повторный bind на :53.
5. `dns.Apply` — переписывание resolv.conf.
6. `syncKillSwitch` — переприменение всего набора nft/iptables.

Плюс фронт после каждой операции делает `load()` = `GET /routing` +
`GET /routing/sources`, а sources — это ещё до 5 с DNS.

Итог: добавление N правил по одному = **O(N²)** вызовов `ip` и резолвов, и после
каждой правки браузер заново учит все маршруты, потому что посредник перезапущен.

Удаление (`server.go:421`) — ровно то же самое.

## Что делать

### 1. Массовый ввод

Транспорт для пакета **уже есть**: `PUT /routing` (`server.go:378`), им пользуется
загрузка файла. Не хватает трёх вещей.

**Формат.** Принимать оба, различая по первому символу (`{`/`[` → JSON, иначе —
список строк):

```json
{ "mode": "vpn_list",
  "rules": [ { "type": "domain", "value": "dtel.ru" },
             { "type": "cidr", "value": "10.0.0.0/8" } ] }
```

Типизация уже жёсткая: `ValidRuleType` + `RoutingRule.Validate`
(`config/rules.go`) — только `ip`/`cidr`/`domain`/`zone`, всё остальное
отвергается. Дополнительно принимать элемент строкой (`"dtel.ru"`) и выводить
тип сам.

Но для ручного набора JSON — шаг назад: уже есть `parseRule()`
(`frontend/composables/useRuleDraft.ts`), который безошибочно выводит тип из
значения. **Основным сделать textarea со списком по строке**, с предпросмотром
(бейдж типа, значение, отметки «дубль»/«плохое») и кнопкой «Добавить N». JSON —
второй принимаемый формат, для переноса между машинами.

**Семантика.** Сейчас импорт `PUT /routing` **затирает весь список** — а тост
говорит «Загружено правил: N» и про потерянные молчит. Нужен выбор
«добавить к текущим / заменить».

**Ошибки поштучно.** `RoutingConfig.Validate` падает на первом плохом правиле и
отвергает всю пачку. Для массового ввода нужен `POST /routing/rules/batch` с
телом `{add: [...], remove: [id...]}`, который валидирует каждое, применяет
годные разом (одно `saveConfig` + одно `applyRoutingNow`) и возвращает
`{added: [...], rejected: [{value, reason}]}`. Заодно дедупликация по значению —
сейчас сервер её не делает вовсе, дубли ловит только UI.

### 2. Сделать само применение дешёвым (главный выигрыш)

**2a. Инкрементальное применение вместо полной пересборки.** Считать разницу
старых и новых правил:

- добавился/удалился `ip`/`cidr` → один `ip route add`/`del`, и всё;
- менялись только `domain`/`zone` → **не трогать посредника DNS вообще**, а
  атомарно подменить `Matcher` в нём (`atomic.Pointer` вместо захвата при
  старте, `routing/matcher.go`). Снять только маршруты исчезнувших имён;
- смена режима или переподключение → полная пересборка, как сейчас.

Это убирает перезапуск :53 и потерю всех выученных маршрутов — самая заметная
пользователю боль после каждой правки.

**2b. Схлопывать всплеск правок.** `applyRoutingNow` заменить на «пометить
грязным» + одна горутина с дебаунсом ~200 мс. Двадцать быстрых правок дадут одну
пересборку. HTTP отвечает сразу, об ошибке применения сообщать через уже
существующий поток событий (`internal/api/events.go`).

**2c. Мелочи, дающие много:**

- резолв доменов в `configureRouting` (`routes.go:113`) распараллелить пулом на
  8, как уже сделано в `rulesource` (`parallel = 8`), и общий дедлайн на всё;
  `ruleResolveTimeout` снизить с 5 с до ~1.5 с;
- `ip -batch -` — один `exec` вместо N; добавить в `iproute.Tool` методы
  `AddRoutes`/`DelRoutes`;
- кэшировать адрес endpoint на время соединения — `setupDefaultVPNRoute`
  резолвит его при **каждом** применении;
- не дёргать `syncKillSwitch`, если для него ничего не изменилось (firewall от
  списка правил не зависит).

### 3. Удаление

- множественный выбор в списке + «удалить выбранные» одним `batch`;
- «удалить хозяйство целиком» — группы уже посчитаны в `useRuleGroups`;
- оптимистичное удаление строки на фронте: сейчас `deleteRule`
  (`RoutingPanel.vue:364`) ждёт полного `load()`.

### 4. Фронт

`addRule`/`deleteRule` после каждой операции делают `load()` → в том числе
`getRoutingSources` с DNS. Дебаунсить `loadSources` и вклеивать возвращённое
сервером правило в список вместо полного перезапроса.

## Порядок

1. `POST /routing/rules/batch` + textarea с предпросмотром (эффект сразу:
   N правил = одно применение).
2. 2c — параллельный резолв и `ip -batch` (дёшево, ускоряет и подключение).
3. 2b — дебаунс применения.
4. 2a — инкрементальное применение без перезапуска посредника (самое крупное,
   делать последним).
5. Множественное удаление и merge-режим импорта.
